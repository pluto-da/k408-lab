# 整机拆解页 · 部件观察模式镜头重做（“绕着元件转、松手就停”）执行 Prompt

## 一、背景与站长原话

站点：考研 408 学习站，线上地址 http://154.8.183.93/pc（整机拆解页）。代码在 `/workspace/fullstack-408`，3D 逻辑集中在 `apps/web/src/pc/engine.ts`（Three.js 0.180 + OrbitControls），页面壳在 `apps/web/src/pages/Pc.tsx`，样式在 `apps/web/src/pc/pc.css`。当前线上版本 v9-e5e2fef。

站长在安卓手机上打开 CPU 与散热器，截图里组装状态是 0/3，画面中间一片空，散热片和两根铜热管挤在屏幕右下角，只露出一半。站长原话：

> 你看我手指滑动之后都跑没了，改成我手指滑动的时候只要不滑动就固定，然后围绕着这个元件能自由观看查看。

这句话里有三个明确要求，必须一个不落地实现：

1. **“跑没了”是 bug，不是操作问题。** 手指一滑，元件就从画面中间漂走，甚至漂出屏幕。必须查到根因并修掉，而不是加个“重置视角”按钮让用户自己救。
2. **“只要不滑动就固定”。** 手指停住，画面就停住；手指抬起，画面也立刻停住。不能有惯性滑行，不能有松手后还在慢慢转、慢慢飘的效果。
3. **“围绕着这个元件能自由观看”。** 旋转的中心必须是元件本身，不是空气中的某个点；而且要“自由”：能从上面、侧面、斜下方看，能转一整圈，能拉近看细节，拉近时元件仍然在中心。

## 二、根因分析（已用无头浏览器实测确认）

我在本地预览环境里用 Playwright 驱动 Chromium，模拟 390×844 手机视口，打开每个部件，读取引擎内部的相机目标点（`controls.target`）和元件实际可见几何体的包围盒中心，结果如下（单位：场景米，c−t 表示“元件实际中心减去旋转中心”）：

| 部件 | 组装状态下 c−t | 组装状态半径 | 全部拆开 c−t |
|---|---|---|---|
| CPU 与散热器 | (0.028, −0.017, 0.035) | 0.046 | 0 |
| 显卡 | (0, −0.039, 0.009) | 0.164 | 0 |
| 内存条 | (0, −0.012, 0.017) | 0.072 | 0 |
| NVMe 固态硬盘 | (0, −0.003, 0.026) | 0.042 | 0 |
| 机械硬盘 | (0.004, −0.041, 0.030) | 0.108 | 0 |
| 网卡 | (0, −0.016, 0) | 0.090 | 0 |
| 电源 | (0, −0.009, 0.035) | 0.129 | 0 |
| 主板 | (0.015, 0, 0) | 0.200 | 0 |

结论非常清楚：

**根因一：旋转中心钉在“全部拆开后”的包围盒中心，而用户刚打开时看到的是“组装状态”。** 打开部件时，`open()` 用内部模型 `meta.bbox`（这是拆开状态的包围盒）算中心，把相机 target 放在那里。可是组装状态下各层被 `L.t` 平移回原位，几何体整体偏到一边。以 CPU 为例，偏移量约 0.047，和 CPU 自身半径 0.046 几乎相等，等于旋转中心落在元件外缘之外。于是双指一转，元件就像挂在一根长杆末端一样绕着空点甩出去，这就是“跑没了”；双指捏合放大时，镜头也是朝那个空点推进，元件被推到画面边缘、再被推出屏幕，这就是截图里画面中间一片黑、散热片挤在右下角的原因。

**根因二：OrbitControls 开启了阻尼惯性。** `enableDamping = true, dampingFactor = 0.08`。手指抬起后，相机会按最后的速度继续转几十帧才停下。配合根因一，甩出去的元件在松手后还会继续飘，用户完全控制不住。这直接违反“只要不滑动就固定”。

**根因三：拆解过程中旋转中心不跟随。** 单指上滑把一层层拆开时，几何体的中心在移动（组装和拆开两种状态中心不同），但相机 target 不动，所以拆的过程中元件也在画面里漂移，拆完和装回的画面中心不一致。

**根因四：单指横向滑动在观察模式里没有任何作用，用户只能用双指转，而双指转又是“旋转+缩放”混在一起。** 用户自然地用单指去拨，结果什么都不转（或者被误判成拆解），只好上双指，一上双指就同时触发缩放，画面一下推近，元件被推出去。手势设计本身就在把用户往 bug 里推。

**根因五：观察模式继承了总览模式的俯仰限制和缩放范围。** `maxPolarAngle = 0.52π` 让人不能从下方看元件（看不到 CPU 底部触点、显卡背板、内存条金手指的背面），`minDistance = 0.05` 又允许镜头钻进元件内部，钻进去后近裁剪面把几何体切掉，也会表现为“东西没了”。

## 三、要做成什么样（交互规格）

### 3.1 旋转中心：永远是元件“此刻”的中心

- 打开任一带内部模型的部件时，旋转中心必须是**当前可见几何体**的包围盒中心（组装状态打开就是组装状态的中心），镜头飞过去时就飞向这个点，打开完成的那一刻元件就在画面正中。
- 单指上滑拆开、下滑装回、点“拆下一层/装回一层”、自动演示时，几何体的中心在变，旋转中心要**平滑跟随**：每一帧把 target 向新中心插值靠近，同时把相机位置平移同样的距离，这样镜头和元件的相对关系不变，视觉上就是“元件始终在中间，层在它周围展开”，不会出现跳动。
- 跟随要平滑（时间常数约 0.1 秒），不能每帧硬跳；拆解是连续拖动的，中心是连续变化的，插值后不会有抖动。
- 在镜头自动飞行（打开、返回、重置视角）的动画进行中，跟随逻辑让位，不和飞行动画抢 target。
- “重置视角”按钮在观察模式下要飞回当前中心、默认方向、默认距离。

### 3.2 松手即停：观察模式没有任何惯性

- 进入观察模式（state = open）时关闭 OrbitControls 阻尼；离开时恢复总览模式原来的阻尼手感。总览页的旋转手感不在这次改动范围内，不能顺手改坏。
- 手指按住不动：画面不动。手指移动：画面严格跟着手指走，一像素对一份角度。手指抬起：当帧停住。
- 自己实现的单指旋转也不允许带速度、带缓动。

### 3.3 手势分配：一根手指也能自由转

手机上最自然的动作是单指拨动，所以单指必须能转；但“单指上滑拆开、下滑装回”是站长之前确认过、页面提示里写着的核心玩法，不能拿掉。解决办法是**方向锁定**：

- 单指按下后先不决定，等手指移动超过约 8 像素时判断方向：
  - 位移明显偏竖直（|dy| > 1.2·|dx|）：锁定为“拆解”，之后这一笔只控制拆解进度，和现在一样；
  - 否则锁定为“环绕观察”：之后这一笔的横向位移控制绕元件水平转（方位角），纵向位移控制俯仰（极角），两个方向都自由，直到抬起手指。
- 一笔之内不允许中途切换模式，避免转着转着突然开始拆。
- 对于没有可拆层的部件（如机箱、主板以外不带层的情况），单指就是 OrbitControls 原生旋转，同样无惯性。
- 双指：保持“捏合缩放 + 双指拖动旋转”，同样绕元件中心、同样无惯性；观察模式下禁止平移（pan），因为平移会把旋转中心挪离元件，这是“跑没了”的另一个来源。
- 鼠标：左键同样走方向锁定（竖拖拆解、横拖环绕），右键旋转，滚轮缩放，桌面行为与手机一致。
- 轻点空白处返回整机的逻辑保持不变（位移小于 8 像素、时长小于 600 毫秒才算轻点），轻点元件本身不响应。

### 3.4 “自由观看”的边界

- 俯仰范围在观察模式放开到接近 0 到 π（各留约 3° 避免万向节翻转），可以从正下方看底面。离开观察模式恢复总览的 0.52π 限制，避免总览时钻到地面以下。
- 缩放范围按元件尺寸定：最近不得进入元件内部（最小距离约为组装半径的 1.6 倍），最远不超过默认取景距离的 2.5 倍，避免缩成一个点。拆开后元件变大，最小距离按拆开半径同步更新。
- 拉近时元件仍在画面中心，因为缩放始终朝旋转中心推进，而旋转中心就是元件中心。

### 3.5 页面文案

元件下方的提示改成和新手势一致的话：“单指上下滑：拆开 / 装回；左右滑：绕着它转。双指：自由旋转、缩放。松手即停。”。页面右侧说明里的“拖动旋转，双指或滚轮缩放。”保持（那是总览的说明，仍然正确）。

## 四、实现方案（落到代码）

只改 `apps/web/src/pc/engine.ts` 的相机与输入部分，以及 `Pc.tsx` 中那一句提示文案；不改模型、材质、灯效、数据旅程、拆解动画本身（`applyDisassembly` 里各层的位移、旋转、缩放公式不动）。

1. **新增实时中心计算** `private updatePivot()`：对当前选中部件的 `interior.group` 先 `updateMatrixWorld(true)`，再用 `Box3.setFromObject` 求世界包围盒中心与半径；缓存到 `this.pivot` 与 `this.pivotR`。在 `applyDisassembly` 末尾调用，使每次拆解进度变化都刷新中心。
2. **打开时飞向组装中心**：`open()` 中摆好内部模型、`applyDisassembly(0)` 之后，用 `updatePivot()` 的结果作为第二段 `flyTo` 的目标；取景距离仍按拆开包围盒算（这样拆开后不会出画），保留原来的视角方向。
3. **每帧平滑跟随**：在 `frame()` 里，`state === "open"` 且没有 key 为 `camera` 的补间时，计算 `delta = (pivot − target)·(1 − e^(−dt/0.1))`，target 和相机位置同时加 delta；有位移就算“moved”，触发重绘。
4. **模式切换**：在 `setState` 中，进入 open 时设 `enableDamping=false`、`enablePan=false`、`minPolarAngle≈0.05`、`maxPolarAngle≈π−0.05`、按半径设 `minDistance/maxDistance`；离开时恢复 `enableDamping=true`、`enablePan=true`、`minPolarAngle=0`、`maxPolarAngle=0.52π`、`minDistance=0.05`、`maxDistance=2.2`。
5. **单指方向锁定**：把 `drag` 结构扩展为 `{ id, x0, y0, lx, ly, k0, h, mode: null | "dis" | "orbit" }`。`onDown` 只登记；`onMove` 在超过阈值时锁定方向；`dis` 分支沿用现有公式；`orbit` 分支用 `Spherical` 以 `controls.target` 为圆心，按 `2π·Δ/画布高度·rotateSpeed` 改 theta 和 phi，夹紧 phi，再 `camera.lookAt(target)`，并取消正在进行的相机补间（用户接管）。抬起或第二根手指落下时结束这一笔。
6. **重置视角**：`frameSelected()` 改用实时中心。
7. **文案**：`Pc.tsx` 第 293 行附近的默认提示换成 3.5 中的话。

## 六、不要做的事

- 不要用“加惯性但更快停”的折中，站长要的是松手即停。
- 不要把单指拆解拿掉或改成按钮，那是已确认的核心玩法。
- 不要在观察模式开放平移，平移是让旋转中心离开元件的第二条路。
- 不要改总览页的手感，不要动模型资源和拆解动画曲线。
- 不要只修 CPU；八个带内部模型的部件全部要验收。

## 七、站长真正想要的体验（需求的深层解读）

站长说“围绕着这个元件能自由观看查看”，背后是一个很具体的学习场景：考研 408 的计算机组成原理部分，要把“CPU、Cache、主存、总线、I/O 设备”这些抽象概念对应到真实硬件上。站长点开 CPU，是想亲眼看清散热器底座怎么压在顶盖上、热管从哪里穿出来、顶盖下面的硅片有多小、触点阵列长什么样；点开内存条，是想看颗粒怎么排布、金手指在哪一边；点开显卡，是想看显存颗粒围着 GPU 核心一圈的布局。这些细节分布在元件的各个面上，有的在顶面，有的在侧面，有的在底面，所以“自由观看”的本质是：**像把一个实物捏在手里翻来覆去地看。**

现实中把东西拿在手里看，有三个特点，这次改动就是要在屏幕上还原这三个特点：

1. **东西始终在手心里。** 手腕怎么转，东西都在眼前，不会转着转着跑到视野外面。对应到屏幕上就是旋转中心等于元件中心，元件永远在画面中间。
2. **手停东西就停。** 现实里不存在“松手后东西自己继续转半圈”的物理现象，那是给地图、相册这种“甩一下翻很远”的场景设计的手感，放在精细观察上反而碍事：用户好不容易对准了想看的角度，一松手又滑走了。对应到屏幕上就是零惯性。
3. **想凑近就凑近，凑近了还是对着它。** 现实里把东西拿到眼前，视线中心还是那个东西。对应到屏幕上就是缩放朝元件中心推进，并且有一个“最近距离”，不能把脸贴进元件里面。

另外，站长是在手机上用的，单手握持、拇指操作是最常见的姿势。双指操作需要两只手或者别扭的单手双指，所以“单指就能转”不是锦上添花，而是手机上能不能顺畅使用的关键。方向锁定的设计让单指同时承担“拆”和“转”两件事：竖着拨是拆，横着拨是转，这和手机上大量应用的直觉一致（例如轮播图横滑翻页、列表竖滑滚动），学习成本几乎为零。

## 八、边界情况与处理办法

1. **拆解动画进行中用户开始旋转。** 允许，两者互不干扰：拆解补间只改各层矩阵，旋转只改相机；中心跟随会把两者统一起来，元件在中间展开，用户同时在转。
2. **镜头飞行动画进行中用户触摸。** 沿用现有逻辑：用户一接管就取消名为 camera 的补间，镜头停在当前位置，然后从这里开始由用户控制。中心跟随在补间被取消后立即恢复工作。
3. **“提示动作”（打开后顶层轻轻抬起再落下）进行中用户触摸。** 竖滑会取消提示动作并接管拆解进度（现有逻辑）；横滑不影响提示动作，让它播完。
4. **单指拨动时第二根手指落下。** 当前这一笔立即结束，交给 OrbitControls 的双指旋转缩放；第二根手指抬起后，剩下的那根手指不继续生效，必须抬起重按，避免误触发拆解。
5. **俯仰转到极限。** 夹紧在约 3° 到 177°，到极限后继续拨不再变化，不会翻转、不会画面倒置。
6. **缩放到极限。** 最近距离按半径计算，拆开后半径变大，最近距离也变大；如果此刻相机比新的最近距离还近，交给 OrbitControls 的下一次 update 自然推回，不做突兀跳变。
7. **机箱（case）这种没有内部模型的部件。** 旋转中心仍是机箱中心，观察模式同样零惯性、禁平移；单指就是原生旋转。
8. **从观察模式返回整机。** 返回动画开始前就恢复总览参数（阻尼、平移、俯仰上限），保证回到总览后手感和以前一模一样；俯仰若超过总览上限，返回的飞行动画本身会把相机带回默认方向，不会卡在地面以下。
9. **桌面端右侧说明面板占位（inset）。** 现有的 `setViewOffset` 让画面中心避开面板，元件中心对齐的是可视区域中心，这一点不受影响。
10. **低端机性能。** 中心计算只在拆解进度变化时做一次包围盒遍历，内部模型网格数量有限，开销可以忽略；每帧跟随只是几次向量运算。静止时（没有拖动、没有补间、中心已对齐）依然按需渲染，不额外耗电。

## 九、为什么不用其他方案

- **只把阻尼系数调大让它快点停：** 仍然有滑行，仍然违背“不滑动就固定”，而且没有解决旋转中心偏离这个真正的“跑没了”根因。
- **改用 TrackballControls 之类的自由轨迹球：** 会引入画面滚转（地平线歪斜），对观察硬件反而更难对准角度；OrbitControls 加上放开俯仰范围已经足够“自由”，还保留了稳定的上方向。
- **把旋转中心固定成拆开状态的中心，只在拆开后才允许旋转：** 用户第一眼看到的就是组装状态，这时候不能转等于把最常用的场景砍掉。
- **单指改成纯旋转、拆解挪到按钮或滑杆：** 违背站长之前确认的“单指上滑拆开、下滑装回”的玩法，提示文案、肌肉记忆都要重来，代价太大。方向锁定能两全。
- **每次拆解完成后自动重新取景（飞一次）：** 会让镜头在用户拖动过程中突然自己动，打断操作。平滑跟随是连续、可预期的，用户感觉不到镜头在动，只感觉元件一直在中间。

## 十、自测脚本要点

自测脚本放在工作区，复用已有的 Playwright 环境（playwright-core + 系统 Chromium，参数带 swiftshader 软件渲染），用 `?debug&dpr=1` 打开页面拿到 `window.__pc` 引擎实例。每个检查项打印：相机目标点、元件实际包围盒中心（遍历内部模型网格实时求）、该中心投影到屏幕的像素坐标、相机到目标距离、拆解进度、相机球坐标的方位角和极角，以及松手后 1.5 秒再取一次的相机位置差。截图保存为每个部件一张、每个关键手势一张，人工再看一遍构图：元件在中间、没有被截断、没有钻进元件内部。全部数字通过后再跑工程检查和构建，然后提交、部署，最后对线上地址再跑一遍关键用例（打开 CPU、双指转、单指横滑、单指上滑），确保线上版本与本地一致。

## 十一、八个部件的观察重点（用于验收时人工看构图）

- **CPU 与散热器：** 组装状态要能从侧面看到热管穿过鳍片、从下方看到底座铜面；拆开后要能看清顶盖、硅片和底部触点阵列的上下关系。
- **内存条：** 能转到正面看颗粒排布，转到侧面看金手指的缺口位置，俯视看颗粒和电路板的厚度关系。
- **显卡：** 能从背面看背板，从侧面看散热鳍片和风扇，拆开后看到核心和围绕核心的显存颗粒。
- **NVMe 固态硬盘：** 体积最小，最容易被推出画面，重点验收拉近后仍居中、看得清主控和闪存颗粒。
- **机械硬盘：** 能看到盘片、磁头臂的相对位置，侧面看清层叠关系。
- **网卡：** 能看到芯片和接口一侧。
- **电源：** 能从风扇面和接口面两个方向看。
- **主板：** 体积最大，重点验收缩小时整块板子能完整入画，拉近时插槽区域仍在中心附近。
