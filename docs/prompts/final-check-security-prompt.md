## 一、站长原话

## 二、我对需求的理解

这句话包含两件事，顺序明确：

**第一件：最后一轮深度检查与优化，目的是“防止出现上述问题”。**“上述问题”指这两天反复出现的几类：画面被讲解面板和按钮遮挡（v18 修过）、界面粗糙不统一（v19 重做过）、以及 v19 遗留的“平板和电脑上结论卡第二行被滚动区裁掉”。站长要的不是再修一处，而是做一次全面体检，把同类问题在全站范围内找出来、修掉，并且建立自动检查，让以后改动时这类问题会被测试拦下，而不是等他在平板上看到再截图反馈。范围不限于化身数据，而是全站：首页、实验室、整机拆解（含原模式、数据旅程、化身数据）、登录注册、条款、隐私等所有页面。

**第二件：安全机制。**站长最直接的担心是“不能让人把代码扒下来”——他花了大量心血做的动画、模拟器、3D 场景、题目数据，不希望别人打开开发者工具或用整站下载工具就能原样拿走、改个名字上线。其次是“等其他专业安全”，也就是一个正式上线网站应有的全套安全：服务器、账号、接口、数据库、传输、依赖、备份、监控。

这里必须先对站长说清楚一个事实，并写进报告：**浏览器要运行的代码，必然会下载到用户的电脑上，所以前端代码不可能做到绝对不被拿走。**任何声称“百分之百防扒”的方案都是假的。专业做法是“提高成本”：让拿到的代码难读、难改、难复用，没有注释、没有可读的名字、没有完整的数据，核心资源不能直接整站下载，盗用时能留下证据。真正不能泄露的东西（账号数据、密钥、未来的付费内容）放在服务器上，只在需要时、给有权限的人返回一小部分。

## 三、现状摸底（执行前已核实）

- 架构：pnpm monorepo，前端 apps/web（React + Vite + three.js），后端 apps/api（Fastify + Prisma + PostgreSQL），Caddy 作为网关与静态文件服务，docker compose 部署在 154.8.183.93，目前只用 IP 走 HTTP，没有域名和 HTTPS。
- 已有安全措施（保留并验证）：Caddy 设置了 nosniff、X-Frame-Options、Referrer-Policy、Permissions-Policy、较严格的 CSP、去掉 Server 头；API 有全局限流（每分钟 300）和登录接口单独限流；密码用 argon2id（OWASP 参数），账号不存在时做假校验防时间侧信道；写请求校验 Origin；Cookie 为 SameSite=Lax；生产构建无 source map；TODO/README 等文档不部署。
- 明显的“代码裸露”问题：
  1. `/legacy/` 下 3.4 MB 的旧版实验室模块（css 16 个、js 约 30 个、three 相关 vendor、body.html）是**未压缩的原始源码**，保留了全部中文、英文注释和可读的变量名，例如 `08-lab.js` 开头就有“实验室外壳。Add a demo with one call: LAB.push(...)”的开发说明。任何人访问 `/legacy/manifest.json` 就能拿到完整文件清单，然后逐个下载。这是目前最大的泄露面。
  2. Vite 主包虽然压缩了，但没有做变量名以外的保护，题目数据、讲解文本、模拟器逻辑都以明文常量存在于 JS 中，用格式化工具一键即可还原结构。
  3. 3D 模型 .glb 文件可被直接下载。
  4. 没有任何防整站爬取的措施（静态资源无频率限制、无防盗链）。
- 运维层面：通过 root + 密钥登录 SSH；服务器的防火墙、SSH 配置、自动安全更新、fail2ban、数据库端口是否暴露、容器是否以 root 运行、备份情况都未核实。

### 2. 全站遮挡与溢出体检（不只化身数据）
建立 `site-audit` 脚本（Playwright），对全站所有路由与关键交互状态（实验室每个演示的初始、运行中、完成态；整机拆解的三种模式；登录注册弹窗；目录展开；菜单打开）在以下视口运行：360×780、393×852、852×393、673×841、884×1104、820×1180、1180×820、1210×800、1366×768、1440×900、1920×1080、2560×1440，每个视口都同时测“实际高度”和“扣除 120 像素浏览器栏”两种情况。检查项：

- 横向溢出为 0；
- 可交互元素两两不重叠，触控设备上尺寸不小于 44×44；
- 浮层（固定定位的工具条、侧栏、抽屉、提示）不遮挡主内容的关键元素（在每个页面声明关键元素选择器，如动画舞台、题干、答案区）；
- 文字不被裁切：检测 `scrollHeight > clientHeight` 且 `overflow: hidden` 的文本容器，以及单行省略号截断出现在关键文本上的情况；
- 文字对比度不低于 4.5:1（大字 3:1）；
- 最小字号不小于 12 CSS 像素；
- 控制台无错误、无未处理的 Promise 拒绝；
- 图片、字体、模型全部加载成功，无 404。

每个失败项给出截图与元素路径。全部修到通过。把 `ride-audit`、`responsive-audit`、`site-audit` 合并为一条 `pnpm audit:ui` 命令，并写入 `pnpm check` 的发布前检查流程（可通过环境变量跳过慢速视口用于日常开发，但部署前必须全跑）。

- 网站上不出现技术说明、开发备注、英文开发注释。（压缩去注释后应自然消失，但仍需扫描页面可见文本。）
- 条款和隐私页与实际的数据收集情况一致（如果新增了安全日志、IP 记录，需在隐私页说明）。

## 五、第二部分：防扒代码（提高拿走和复用的成本）

### 1. 旧版模块（/legacy）全部纳入构建
- 用 esbuild 或 terser 对 legacy 的每个 JS 做压缩：删除全部注释、合并空白、局部变量重命名（mangle）、常量折叠；CSS 用 lightningcss 或 cssnano 压缩并去注释；body.html 压缩去注释。
- 文件名加内容哈希（例如 `legacy/js/08-lab.3f9a1c.js`），manifest 改为构建时生成，只含哈希文件名；不再提供可读的分组名。可以进一步把同时加载的模块合并成少数几个包，减少可枚举的文件数量。
- 源目录 apps/web/public/legacy 改为 apps/web/legacy-src（不再被 Vite 原样复制），由构建脚本输出到 dist/legacy。确保原始未压缩文件不会进入 dist。
- 注意保持 legacy 代码依赖的全局名称（如 window.LAB、window.MB_GLB_BUF、__LEGACY_LOAD__ 等跨文件接口）不被重命名：用 terser 的 `mangle: { toplevel: false }` 并保留全局属性，压缩后跑完整的实验室回归。

### 2. 核心逻辑混淆
- 对最有价值、最可能被抄的部分（化身数据模拟器与场景、整机拆解 3D 逻辑、各实验室动画核心、题目与讲解数据）在生产构建中额外做一层混淆：使用 javascript-obfuscator（或 Vite 插件形式）对指定分块启用字符串数组编码、控制流扁平化（低强度）、标识符十六进制化。只对这些分块启用，不对 React、three.js 等第三方库启用，以控制体积与性能损失。
- 性能预算：混淆后首屏 JS 体积增长不超过 20%，化身数据帧率下降不超过 5%（用同一软件渲染环境对比测量），实验室动画无卡顿。超出就降低混淆强度。
- 题目、讲解等大段文本数据：从 JS 常量中拆出，构建时以简单的编码（例如 XOR + base64，按分块不同的密钥）打包成二进制资源，运行时解码。这不是加密（密钥必然在前端），目的是让搜索文本、直接复制数据变得麻烦。若后续有会员内容，则改为登录后由 API 分段返回。

### 3. 资源防整站下载
- Caddy 层对 `/legacy/*`、`/assets/*`、`.glb` 等静态资源加频率限制（需要 caddy-ratelimit 插件，构建自定义 Caddy 镜像；若插件不可用，则在 Caddy 前或 API 侧用其他方式实现，或至少对 manifest 等枚举入口限流），对短时间内大量请求的同一 IP 返回 429。阈值要保证正常用户一次完整浏览不受影响（先统计一次正常浏览全站的请求数，再设为其 3~5 倍）。
- 防盗链：静态资源检查 Referer，非本站来源（空 Referer 允许，以免影响直接访问和部分浏览器）的 .glb、legacy 资源返回 403。
- 屏蔽常见整站下载工具的 User-Agent（HTTrack、wget、curl 默认 UA、python-requests、Scrapy 等）访问静态资源；这只能挡住不懂行的人，但成本很低。
- robots.txt 允许搜索引擎抓取页面，禁止抓取 `/legacy/`、`/assets/`、`/api/`。

### 4. 版权与追溯
- 每个页面底部和压缩后 JS 文件头保留一行版权声明（“© 2026 考研408 动画实验室 保留所有权利”），压缩时用 `/*! ... */` 保留。
- 在混淆代码中嵌入不可见的版权指纹（例如若干无副作用的特征常量），日后发现抄袭站点时可用来比对证明来源。指纹清单只保存在内部文件，不部署。
- 条款页补充：禁止复制、抓取、镜像、反向工程本站代码与内容。

### 5. 不做的事（并在报告中解释理由）
- 不禁用右键、不禁用 F12、不做“检测到开发者工具就清空页面”。这些手段对懂行的人无效（一行脚本就能绕过），却会误伤正常用户（读屏、翻译插件、复制题目做笔记），还可能被搜索引擎判为不友好。
- 不用无限 debugger 陷阱，它会让部分浏览器卡死。

## 六、第三部分：其他专业安全

### 1. 传输：HTTPS
- 目前只有 IP，无法申请正式证书。报告中明确：**强烈建议站长购买一个域名并解析到服务器**，Caddy 配置已支持设置 DOMAIN 自动申请证书。若站长提供域名，则切换 HTTPS、开启 HSTS（max-age 先设一周，稳定后一年）、Cookie 加 Secure、HTTP 自动跳转。没有域名前，这一项保持现状，但在报告里标记为最高优先级待办。（中国大陆服务器使用域名还需要备案，报告中提醒。）

### 2. 服务器加固
执行前先备份当前配置，每一步都确认 SSH 仍能用现有密钥登录后再进行下一步，避免把自己锁在外面。
- SSH：确认密钥登录有效后，禁用密码登录（`PasswordAuthentication no`），root 只允许密钥登录（`PermitRootLogin prohibit-password`），限制尝试次数。**更改 SSH 端口或禁用 root 属于有锁死风险的操作，本次不做，只在报告中建议。**
- 防火墙：ufw 只放行 22、80、443，默认拒绝入站；确认 docker 发布的端口不会绕过 ufw（docker 会直接写 iptables，需要检查 PostgreSQL 5432、API 3000 没有发布到公网，只在内部网络）。
- 安装 fail2ban 保护 SSH。
- 开启 unattended-upgrades 自动安装安全更新。
- 检查服务器上有无多余的服务、开放端口（`ss -tlnp`）、可疑账号和计划任务。

### 3. 容器与密钥
- API、web 容器以非 root 用户运行；文件系统只读（必要的临时目录除外）；去掉不需要的 Linux capabilities（`cap_drop: ALL`）；设置 `no-new-privileges`；限制内存与 CPU。
- 检查 .env：JWT_SECRET、数据库密码长度足够（≥32 字节随机），文件权限 600，不在镜像里、不在 Git 里。
- 镜像只包含运行所需文件，不含源码、测试、文档。

### 4. 应用层
- 逐个检查 API 路由：输入全部经 zod 校验；错误信息不泄露堆栈和内部细节；未登录、越权访问返回正确状态码。
- 认证：JWT 有效期与刷新策略合理；退出登录使令牌失效；连续登录失败按账号和 IP 双维度限流并逐步延长等待；注册防批量（同 IP 频率限制，必要时加简单的人机验证题，不依赖第三方服务）；密码最小长度与常见弱密码拦截。
- 删除线上遗留测试账号 e2e1791465270（这个是此前创建的测试账号，删除前确认它不是站长本人的账号——查看注册时间与邮箱前缀，属于测试数据即删除）。
- 安全响应头复查：CSP 去掉不必要的放宽；加 `Cross-Origin-Resource-Policy: same-origin`（对 legacy 与模型资源）；`X-Frame-Options` 与 `frame-ancestors` 一致。
- API 响应加 `Cache-Control: no-store`（涉及账号信息的接口）。

### 5. 依赖与代码
- `pnpm audit` 修复高危及以上漏洞；检查 three.js、Fastify、Prisma 等主要依赖版本。
- 搜索仓库与构建产物中是否误含密钥、内网地址、服务器密码、私钥。

### 6. 数据库与备份
- PostgreSQL 不暴露公网，使用强密码。
- 每日自动备份数据库（pg_dump 压缩，保留 7 天），备份文件权限 600；做一次恢复演练，确认备份可用。

### 7. 日志与监控
- Caddy 访问日志开启并按大小轮转（不记录 Cookie、Authorization）；API 记录认证失败、限流触发等安全事件。
- 隐私页说明会记录 IP 与访问日志用于安全防护，保留 30 天。

## 十、风险分析与取舍

### 1. 混淆带来的风险
混淆会让线上报错难以定位。对策：构建时生成 source map 但**不部署**，只保存在本地工作目录（不进 Git、不上服务器），线上报错时用它在本地还原调用栈。混淆也可能破坏依赖函数名、属性名的代码（例如通过字符串访问对象属性、依赖 `Function.name` 的逻辑），所以混淆范围要逐个分块启用，每启用一个分块就跑一遍对应页面的回归和 audit:ui。若某个分块混淆后出现问题且两次修复不成功，就对该分块只做压缩不做混淆，并在报告里列出。

### 2. 限流与防盗链误伤
学校、公司、宿舍网络常常很多人共用一个出口 IP，阈值过低会误伤真实学生。对策：先在测试环境用脚本模拟一个用户完整浏览全站（首页、所有实验室、整机拆解三种模式、化身数据完整一条路线）统计请求数，阈值设为其 5 倍，并且只对静态资源中体积大、价值高的部分（legacy、模型）启用严格阈值；页面本身和 API 保持现有限流。被限流时返回友好的中文提示页而不是空白。防盗链只拦截明确来自其他站点的 Referer，空 Referer 放行，避免影响从收藏夹、微信内置浏览器直接打开的用户。

### 3. 服务器加固的锁死风险
每一步改动都按“改配置 → 保持当前会话不断开 → 新开一个会话用密钥登录验证 → 成功后再继续”的方式进行；ufw 启用前先放行 22 端口；sshd 配置修改后先用 `sshd -t` 检查语法再重载。任何一步验证失败立即回滚到备份配置。云服务器控制台通常还有一层安全组，报告中提醒站长同步在云控制台只放行 22、80、443。

### 4. 性能与体验
所有安全措施都不能让学生感到网站变慢或变难用。验收时对比 v19 与 v20 的首屏加载时间（同一网络条件下取三次平均）、化身数据帧率、实验室动画流畅度，任一项明显变差都要调整。

## 十一、给站长的报告格式

报告用通俗的话说明：做了哪些检查、修了哪些问题（附前后对比截图）；防扒做到了什么程度，别人现在打开开发者工具能看到什么、看不到什么（附一张混淆前后代码对比截图）；服务器和账号层面加了哪些保护；还有哪些需要站长自己决定或操作的事项（买域名与备案、云控制台安全组、是否修改 SSH 端口），按优先级排列。

## 十二、各类问题的根因与长效机制

回顾这两天的问题，根因有三类，每一类都要有对应的长效机制，而不是只修表面：

1. **只在电脑大屏上自测**。遮挡问题之所以到站长平板上才暴露，是因为开发时默认在宽屏下看效果。长效机制：audit:ui 的视口清单必须包含“扣除浏览器栏”的真实可视高度，每次部署前强制全跑，失败就不部署。
2. **布局靠固定数值硬凑**。早期用固定比例偏移镜头、固定高度放面板，内容一多或屏幕一矮就出问题。长效机制：所有浮层与面板使用弹性布局和容器查询，关键文本容器禁止 `overflow: hidden` 加固定高度的组合（lint 规则或审计脚本检查）。
3. **缺少设计规范**。按钮、颜色、间距各写各的，导致界面不统一。长效机制：v19 建立的 --ride-* 变量推广为全站设计变量文档（内部文件，不部署），新组件只能用变量；审计脚本检查按钮高度和颜色是否来自变量集合。

把这三条写进仓库内部的开发规范文件（不部署），以后任何改动都按它自查。

## 十三、完成定义

站长在手机、平板、电脑上打开网站任意页面，看不到遮挡、裁切和错位；别人想整站下载或直接复制代码时，只能拿到压缩混淆、没有注释、难以复用的文件，大资源下载被限流或拒绝；服务器只开放必要端口，账号、数据库和备份都有保护；所有检查自动化，下次改动时同类问题会被提前拦下。
