# 〇、这份 Prompt 怎么用

这是一份交给制作者（人或智能体）的完整制作说明。第一版成片已经做出，用户的反馈只有一句话：“磕磕绊绊，视频内容还卡，声音还 AI”。第二版的全部目标，就是把这句话里的三个问题——**节奏磕绊、画面卡顿、声音机械**——从根上解决，同时把成片的质感拉到“像一家认真做产品的团队发布的片子”的水平。

请按顺序阅读：第一章说清用户真正要什么；第二章拆解参考范例并给出仿照结论；第三章是创意和逐镜分镜；第四章是能在本沙盒（无 GPU、两核 CPU、约 7GB 内存、单条命令 120 秒上限）落地的技术方案；第五章是平台规范；第六章是验收清单；第七章是风险与回退。凡是写着“需用户决定”的地方，制作者不得自行替用户选择。

硬约束（任何时候都不能违反）：

1. 网站源码 `/workspace/fullstack-408` 只读，不改仓库，不碰服务器；只以普通访客身份打开线上页面 `http://154.8.183.93` 录制画面。另一个任务正在部署 v20，正式录制必须等 v20 上线且页面稳定后进行，录制前先确认首页与各实验能正常打开。

3. 不允许用静态截图做推拉来冒充视频；每一个镜头里，画面内容本身必须在动。

# 一、需求深度剖析

## 1.1 用户说了什么，没说出口的是什么

用户的原话很短，但每个词都指向一个具体的技术原因：

| 用户的话 | 观众感受到的问题 | 第一版的真实原因 |
|---|---|---|
| “磕磕绊绊” | 镜头之间衔接生硬，节奏一顿一顿，像幻灯片 | 大量 0.3 秒交叉溶解；镜头长度跟着旁白句子走，不跟音乐节拍走；转场点和重音不对齐 |
| “视频内容还卡” | 动画跳帧、掉帧，3D 画面像定格 | 沙盒里 3D 实时渲染只有约 1 帧每秒；3D 和化身数据只能用静帧推拉；实验室动画按 0.3～1 秒间隔截图再溶解，等于 1～3 帧每秒的动画 |
| “声音还 AI” | 旁白平、字字等长、没有呼吸和语气 | 使用离线小模型女声，韵律机械；在线高质量音色因握手被拒用不了 |

所以第二版不是“改改文案、换个音乐”，而是要换掉**录制方式**（实时录屏 → 虚拟时间逐帧渲染）、换掉**剪辑逻辑**（跟句子剪 → 跟节拍剪）、换掉**声音来源**（离线小模型 → 真人或顶级云端音色）。

## 1.2 从历史要求推断出的用户画像

综合用户前后提出的要求，可以确定这是一位标准很高、在意“专业感”的创作者：

- 要专业感：不能像学生作业或模板套片，要像正经产品的发布片。
- 要流畅：动画必须丝滑，镜头运动要有加减速，不能一卡一卡。
- 不要机械感：声音要像真人说话，有停顿、有轻重、有情绪。
- 全平台分发：抖音、小红书、视频号用竖屏，B 站和站内嵌入用横屏。
- 时长 30 秒到一分半：竖屏约 45 秒，横屏约 75 秒。
- 要旁白和音乐：默认有人声；但如果人声达不到“自然”的标准，宁可不要人声，也不能再出现机械声。
- 主动要求“去看别人怎么做的，仿照一个优秀范例”：说明用户希望有一个清晰的、业界公认的质量标杆，而不是制作者自由发挥。

## 1.3 成片要让观众得到什么

目标观众是备考 408 的学生（大三大四在校生、跨考生、二战考生），刷短视频时注意力只有两三秒。他们的痛点不是“记不住”，而是“看不见”：地址怎么一步步翻译、页面怎么被换出、拥塞窗口怎么涨跌，全靠脑补。成片只需要让他们在 45 秒里相信一件事：**这个网站能把看不见的过程，变成看得见、点得动的动画，而且免费、手机就能打开。**

## 1.4 验收标准总表（详见第六章）

| 维度 | 标准 |
|---|---|
| 帧率 | 成片恒定 60 帧每秒；所有运动镜头逐帧不同，不存在重复帧冒充的“伪 60 帧” |
| 画面真实性 | 每个镜头的画面来源都是逐帧渲染的真实页面序列；镜头推拉只能叠加在“本身在动”的画面上 |
| 节奏 | 剪辑点落在音乐节拍上，误差不超过 1 帧；关键词字幕与对应口播字的出现误差不超过 3 帧 |
| 人声 | 盲听不应被一耳朵听出是合成音；无读错字（408、Cache、TLB 等读法统一）；语速每秒 4～4.5 字，句间有自然换气 |
| 字幕 | 与口播逐字一致；全部落在平台安全区内；单行不超过 14 个字 |
| 声音 | 整体响度 -14 LUFS（±1），真峰值不高于 -1 dBTP；人声出现时音乐自动压低 6～9 dB |

# 二、范例拆解与仿照结论

说明：以下拆解基于公开的发布片页面、专业拆片网站的逐镜分析和页面元数据整理；制作开始前，制作者应亲自把主仿照范例逐帧看一遍，用秒表核对节奏。

## 2.1 范例清单

**范例 1：Linear 功能发布片（主仿照）**

- 代表作：Introducing Linear Releases（约 30 秒，https://www.youtube.com/watch?v=6dIwFoQ0eVg ，拆解见 https://impractical.ai/launch-videos/linear-linear-releases ）；Introducing Linear Diffs（约 52 秒，https://www.youtube.com/watch?v=7gZBxBTapDQ ，拆解见 https://impractical.ai/launch-videos/linear-linear-diffs ）；Introducing Linear for Agents（33 秒，拆解页给出“无旁白、每分钟 20.2 个镜头、两次音乐切换”，即平均每镜约 3 秒，见 https://videngineer.com/teardowns/motion-graphics/linear-introducing-linear-for-agents/ ）。
- 结构：一个功能一支片；开头直接上界面，不铺垫；中段两三个使用瞬间；结尾品牌与链接。
- 开头钩子：第一帧就是产品界面本身，配一句极短的大字。
- 节奏：平均每镜 2～3 秒；静态界面上始终有缓慢的“镜头漂移”，关键交互时突然“推近”（punch-in）到某个按钮、徽标或数字上。
- 镜头运动：缓慢、连续的漂移，像在一个建筑空间里移动；推近时用急加速、长减速的缓动曲线，没有回弹。
- 界面展示：全部是真实产品界面，不重绘；用浅景深虚化无关的侧栏，把视线锁在交互点；用匹配剪辑让两个界面的网格对齐过渡。
- 字幕与文字：大字号、单一字重、静止不乱动，文字本身就是“旁白”，静音也能看懂。
- 配乐：稀疏、节奏感强的声音设计，用来标记事件而不是填满时间；硬切落在节拍上。
- 人声：基本没有。

**范例 2：Raycast 新版上线片 “It's out”（辅助：竖屏的速度感）**

- 链接：https://www.youtube.com/watch?v=uJ70iGerYzE ，拆解见 https://impractical.ai/launch-videos/raycast-its-out 。预热片 “New Raycast. Coming 2026” 39 秒，第一秒就出现搜索框，第四秒已经在输入（见 https://www.contentcabinet.in/insights/product-launch-video-examples ）。
- 手法：整支片围绕一条强驱动的音乐剪辑，每一个硬切都落在拍点上，不用任何溶解；镜头视野收得很紧，用快速推近隔离单条命令；粗大的动态文字在两个界面镜头之间闪现，停留时间刚好够读完，下一拍就切走。
- 借鉴点：竖屏版的“递进演示”段落用它的节拍硬切法。

**范例 3：Brilliant 学习平台电视广告（辅助：同品类的叙事与人声）**

- 链接：“Thousands of Interactive Lessons” https://www.ispot.tv/ad/qa53/brilliantorg-thousands-of-interactive-lessons （另有 “Best Way to Learn Math & Science” 等同系列）。
- 手法：直接展示在网页上学习的样子——彩色的可交互图形和题目铺满屏幕，强调“动手学比看讲座更有效”，结尾引导免费开始。
- 借鉴点：它是和本站最接近的品类（交互式可视化学习）。它证明了“学习产品”的宣传片可以完全靠真实交互画面撑起来，旁白负责点出“为什么这样学更好”，语气轻松、像朋友推荐，不是播音腔。

**范例 4：Notion 3.0 发布片与 v0 发布片（参考：前三秒立论）**

- Notion 3.0：90 秒、无旁白，第三秒整句卖点就上屏，第四秒产品出现。v0：48 秒、无旁白、无真人，输入框是主角，结尾停在网址上。资料见 https://www.contentcabinet.in/insights/product-launch-video-examples 。
- 借鉴点：卖点必须在前 3～5 秒出现；结尾停在网址上并给足阅读时间。它们也证明了“纯音乐 + 动态文字”完全可以撑起一支高质量发布片，这是本项目的保底方案。

**范例 5：3Blue1Brown 式可视化（参考：动画即解释）**

- 资料：https://www.3blue1brown.com/lessons/manim-demo 。这一风格的核心是“图形随着讲解一笔一笔长出来”，观众从不会一边读一样东西、一边听另一样东西；人声在混音里永远第一，音乐垫在下面。
- 借鉴点：化身数据段落里，地址被切成虚页号和页内偏移、快表查找、页表翻译，每一步画面都要和旁白同步“长出来”，而不是一张完成的图摆在那里被描述。

**范例 6：B 站同类工具推广视频（参考：国内受众的痛点话术）**

- 代表：B 站 UP 主“图码”的《数据结构与算法-代码可视化神器》（5 分 23 秒，约 1.5 万播放、906 收藏，https://www.bilibili.com/video/BV1ZDPmztEee/ ），同合集还有《别再死记硬背了，用可视化学习数据结构和算法》等标题。
- 观察：国内同类视频多为长时间录屏讲解，标题话术集中在“别再死记硬背”“看得见”“神器”。这说明痛点话术是对的，但短视频平台上 5 分钟录屏留不住人——我们取其话术、弃其形式。

**范例 7：短视频平台“黄金三秒”的通用规律（参考：数据）**

- 公开的运营分析指出，爆款视频前 3 秒平均镜头切换 2.7 次，普通视频约 1.2 次；开头加入短促音效可提升前 3 秒留存（见 https://www.chanmama.com/yunyingquan/article/1176.html ）。另有拆片框架总结：赢家的节奏多为“开头三秒很密、中段演示放稳、结尾前再加速”。
- 借鉴点：竖屏开头 3 秒内安排 2～3 个镜头变化（可以是同一镜头内的推近和文字切换），中段放稳，片尾前加速收束。

## 2.2 仿照结论

**主仿照：Linear 功能发布片的视觉语法。** 理由有三。第一，本站最大的资产就是“真实在动的界面”——排序柱子在交换、3D 电脑在拆开、虚拟地址在穿行，Linear 的语法正是“界面即主角”，最能把真实界面拍出高级感，而且不需要演员、不需要绘制素材。第二，Linear 的高级感来自克制：少量动作行为反复使用、大字静止、硬切落拍、缓慢漂移加精准推近，这些全部可以用代码精确实现，不依赖图形工作站软件，适合在本沙盒里做。第三，它的节奏模型（每镜 2～3 秒、硬切落拍）天然解决第一版“磕磕绊绊”的问题。

**辅助一：Brilliant 的叙事与人声。** Linear 几乎没有旁白，而用户要旁白。我们借 Brilliant 的方式：旁白像一位学长在旁边轻声推荐，负责解释“为什么这样学有用”，画面负责证明。

**辅助二：Raycast 的节拍硬切与动态文字。** 竖屏版需要更强的速度感，演示段落借用它“每拍一切、文字闪现”的方法。

**不照搬的部分：** 不照搬 Linear 的深色配色和字体，使用本站自己的配色与界面；不照搬 Raycast 的极端快切（学习类内容需要让观众看清一步）。

# 三、整体创意与脚本

## 3.1 一句话创意

**“你背过的那些概念，其实一直在动。”** 全片以“看见”为线索：开头用最具冲击力的第一人称访存画面告诉观众“页表原来长这样”，中段用三段真实交互递进（实验室 → 整机拆解 → 化身数据），结尾落在“手机打开、免费、今天就看明白”。

## 3.2 视觉系统（全片统一，不得逐镜发挥）

- 画面来源：全部来自线上页面的 60 帧逐帧渲染序列；录制分辨率为成片的 1.5～2 倍，以便推近时不糊。
- 底色：沿用站点自身的深色背景；片头片尾卡与过渡标题使用站点主色作为唯一强调色。
- 镜头行为只用四种，全片反复使用：①缓慢漂移（每秒位移不超过画面宽度的 1.5%，缩放从 100% 到 106%）；②精准推近（8～12 帧内从 100% 到 130%～160%，急加速长减速）；③节拍硬切；④匹配剪辑（前后两个镜头的关键元素位置对齐）。不使用翻页、旋转、闪白、故障风等花哨转场。
- 缓动曲线：漂移用平缓的两端减速曲线（cubic-bezier(0.45, 0, 0.55, 1)）；推近用急加速长减速曲线（cubic-bezier(0.16, 1, 0.3, 1)）；禁止线性运动和回弹。
- 景深：推近到某个控件时，其余区域加 6～10 像素的高斯模糊并压暗 25%，视线锁定在交互点。
- 光标：电脑画面使用程序合成的光标（放大到系统光标的 1.6 倍），沿平滑贝塞尔曲线移动，点击时有一圈淡色涟漪；手机画面用圆形触点代替光标。光标的点击时刻必须与页面上真实点击发生的虚拟时刻完全一致。
- 设备框：竖屏的“多端”镜头可以使用简洁的手机、平板、笔记本外框，外框只做轻微的三维倾斜（不超过 12 度），不加反光贴图；其余镜头不加设备框，界面铺满。
- 字体：标题用思源黑体（Noto Sans CJK）Heavy 或 Bold，正文字幕用 Medium；数字和英文缩写用同一字体家族；全片不超过两种字重。
- 动态文字：标题文字从基线向上遮罩显现（6～8 帧），停留至少 1.2 秒，退出时整体淡出 4 帧；同一时间屏幕上最多一个大标题、一行口播字幕。

## 3.3 节拍网格

选择 **120 BPM** 的配乐（若选中的曲目不是 120 BPM，按其实际速度换算）。120 BPM 时一拍 0.5 秒、一小节 2 秒；在 60 帧每秒下，一拍正好 30 帧、一小节 120 帧，便于把镜头长度写成“几小节”。所有剪辑点优先落在小节第一拍（重拍），次选落在第三拍；推近动作的起点落在拍点上。

## 3.4 旁白写法

- 口语化、短句、像学长在旁边说话；每句不超过 18 个字；避免书面语和广告腔（“全新”“极致”“赋能”之类一律不用）。
- 语速每秒 4～4.5 字；句与句之间留 0.2～0.4 秒换气；关键词前可以留 0.15 秒微停。
- 网址是数字形式，读出来拗口，第二版**不念网址**，改为“网址就在屏幕上”，网址只在画面上大字呈现。
- 读音统一：“408”读作“四零八”；“Cache”读作英文“cache”，字幕写“Cache”；“TLB”在旁白里统一说“快表”，字幕可写“快表（TLB）”。

## 3.5 竖屏版分镜（9:16，1080×1920，约 45 秒，60 帧每秒）

安全区：关键文字与主体放在横向 108～972 像素、纵向 288～1540 像素的范围内；口播字幕基线放在纵向约 1400 像素处；大标题放在纵向 300～700 像素区域。

| 镜号 | 时间 | 时长 | 画面 | 镜头运动 | 旁白 | 屏幕文字 | 音乐卡点 |

## 3.7 开头三秒与结尾的专门要求

- 第一帧必须是有信息量的运动画面，不允许黑场、不允许标志动画、不允许“大家好”。
- 前 3 秒内至少有 2 次视觉变化（推近一次、文字切换一次）和 1 个短促音效。
- 片尾网址停留不少于 3 秒，网址字号在竖屏不小于 96 像素、横屏不小于 84 像素；片尾卡最后 0.5 秒保持静止，便于平台截取封面和循环播放时不突兀。

# 四、技术实施方案

## 4.1 总体流程

脚本定稿 → 选定配音方案并完成配音（先有声音，后定画面长度）→ 选定配乐并标注节拍网格 → 按“拍”生成剪辑时间线 → 虚拟时间逐帧录制各镜头素材 → 程序化合成（镜头运动、光标、景深、文字、字幕）→ 混音与响度标准化 → 编码输出 → 逐项验收。

## 4.2 解决卡顿：虚拟时间逐帧渲染

**原理。** 页面的所有动画都依赖时间函数：`requestAnimationFrame`、`performance.now`、`Date`、`setTimeout`、`setInterval`，以及 CSS 动画和网页动画接口。如果在页面脚本运行之前把这些函数全部替换成一个“虚拟时钟”，就可以由录制程序决定时间何时前进：每次只让时间前进 1/60 秒，等页面把这一帧完整画好，再截图；哪怕一帧要画 1 秒钟，录出来的序列在时间上也是严格均匀的 60 帧。这正是开源工具 timesnap / timecut 的做法：它在页面加载前覆盖 `new Date()`、`Date.now`、`performance.now`、`requestAnimationFrame`、`setTimeout`、`setInterval` 及对应的取消函数，使页面在虚拟时间线上运行，从而实现“比实时更慢地录制、成片依然平滑”（见 https://github.com/tungs/timecut 与 https://github.com/tungs/timesnap ）。

**对本站是否可行。** 已核对源码（只读）：3D 引擎用 `THREE.Clock` 计时（底层就是 `performance.now`），每帧的时间步长被限制在 0.1 秒以内，补间动画也用 `performance.now`；渲染循环通过 `renderer.setAnimationLoop` 驱动，最终调用的是窗口上的 `requestAnimationFrame`。因此只要在页面脚本之前注入时间替换，3D 场景、化身数据、实验室动画都会严格按虚拟时间运行。另外，化身数据页内置的调试接口（如跳站函数）只在审计构建中开启，线上版本不能依赖，镜头的起点需要通过真实点击界面来到达。

**实施步骤。**

1. 环境准备：确认可用的浏览器内核。注意：本次研究时发现沙盒里 `/usr/bin/chromium` 已不存在，两次尝试自动下载浏览器均失败，正式制作前必须先恢复一个可用的无头浏览器（重新安装系统浏览器包，或由用户/上级任务提供），这是逐帧录制的前置条件。
2. 写一个时间替换脚本，通过 `page.addInitScript` 在每个页面加载前注入。脚本维护一个虚拟时间 `vt`，提供 `advance(ms)`：先按到期顺序执行所有到期的定时器，再把 `vt` 推进到目标值，接着把所有网页动画暂停并把当前时间加上 `ms`（覆盖 CSS 动画与过渡），最后一次性执行本轮登记的所有 `requestAnimationFrame` 回调。研究阶段写好的原型在 `/workspace/work/promo2/vt-probe.cjs`，可直接作为起点。
3. 加载阶段用“混合时间”：网络请求是真实的，页面加载、字体和模型下载期间，每过 250 毫秒真实时间推进 50 毫秒虚拟时间，直到加载提示消失、模型就位；正式录制开始前把这段时间排除在外。
4. 交互用真实点击：录制脚本在指定的虚拟时刻调用真实的点击（例如点“播放”、改参数、点“出发”），同时把点击坐标和时刻写入一份交互日志，供后期合成光标和涟漪使用，保证光标与界面反应严格同步。
5. 逐帧截图：每帧执行“推进 16.667 毫秒 → 等待一次渲染完成 → 截图”。截图用无损 PNG，录制分辨率取成片的 1.5～2 倍（横屏素材 2880×1620 或 2560×1440；竖屏手机画面用 393×852 视口、设备像素比 3）。
6. 分段与续录：单条命令只有 120 秒，且不能后台常驻进程。因此每个镜头拆成若干段，每段不超过约 80 帧（3D 画面按约 1 秒一帧估算）；每段开始时重新打开页面并用“快进”把虚拟时间推进到该段起点（快进时不截图、每次推进 16.667 毫秒，以保证 3D 场景状态与逐帧录制完全一致）。若快进本身耗时过长，就把镜头设计成从一个可通过点击直接到达的状态开始（例如化身数据的某一站、某个实验的初始状态），每段只录 1～2 拍。开工第一步先实测：在 1440p 下 3D 页面每帧耗时多少、实验室页面每帧耗时多少，据此重排分段表。
7. 合成为视频：每段 PNG 序列用 `ffmpeg -framerate 60` 编成无损或高码率中间文件（建议 FFV1 或 CRF 10 的 H.264 全帧内），镜头内各段直接拼接，拼接处逐帧比对确认没有重复帧或跳帧。
8. 备选的更强确定性方案：若遇到替换不到的时间源（例如工作线程、视频元素、音频时钟），改用浏览器调试协议的“受控出帧”能力（无头模式下由录制程序逐帧下发出帧指令），或用调试协议的虚拟时间策略；两者都要求浏览器以对应参数启动，需先小样验证。

**程序化镜头运动。** 所有推拉摇移在后期合成阶段完成，而不是在录制时移动页面：对每一帧按时间线计算缩放倍数和中心点，用浮点精度的仿射变换（双三次插值）从高分辨率素材中取景。不要用 ffmpeg 的 zoompan 滤镜做缓慢推近——它的坐标取整会造成细微抖动；如果一定要用 ffmpeg，先把素材放大 4 倍再取景。缓动曲线按 3.2 节的两条贝塞尔曲线实现，推近起点对齐拍点。

**为什么不选 Remotion 做主线。** Remotion 是成熟的程序化视频框架，个人和 3 人以内团队可以免费商用（见 https://www.remotion.dev/docs/license/faq ），三维场景要用它的专用画布组件并由它的帧号驱动。但本片的画面来源是线上真实网站，不能改源码，也无法把网站嵌进 Remotion 里逐帧驱动；而且它同样需要可用的浏览器内核和较大的依赖安装。所以主线是“虚拟时间录制真实网站 + Python 合成”，Remotion 只作为可选的片头片尾与文字动画工具（若安装顺利）。

2. **不想录音就选 B（豆包 2.0）**：中文自然度和语气控制在云端方案里最强之一，免费额度足够本项目；若用户已有阿里云账号，C 同样可以。
3. **无论选哪种，都同步做一版 H（纯音乐 + 动态文字）**：它不依赖任何外部条件，可以先交付，也作为人声版不达标时的保底。

**配音制作要求（适用于 B～G）：** 逐句合成，不整段合成；每句生成 3 个版本挑选；用接口自带的字级时间戳（或用语音识别做强制对齐）得到每个字的时刻，作为文字上屏和推近动作的锚点；人声干声统一 48kHz，轻度压缩，-16 LUFS 左右再进总混。

## 4.4 音乐

**曲库：**

- Pixabay Music：遵循 Pixabay 内容许可，可商用、无需署名；但部分曲目被作者登记了版权识别，上传后可能被自动认领，下载时保存许可证书以便申诉（见 https://pixabay.com/service/faq/ 与 https://pixabay.com/blog/posts/how-to-clear-a-youtube-content-id-claim-with-a-pix-190/ ）。优先挑选页面上没有“版权识别”盾牌标记的曲目。注意 Pixabay 的开放接口不提供音乐下载，需在网页上下载，可能需要账号。
- YouTube 音频库：曲目可免费用于视频，部分曲目要求署名；需要登录用户自己的 YouTube 工作室下载。
- Free Music Archive：逐首查看许可，只用 CC0 或 CC BY，避开“非商业”与“禁止演绎”许可。
- 保底：用程序原创合成，但必须比第一版更讲究（真实采样的钢琴和合成器音色、有动态的鼓组），否则宁可用曲库。

**曲风：** 竖屏用 118～124 BPM 的轻电子 / 未来车库 / 极简科技风：干净的拨弦与钢琴、低频冲击、有清楚的段落升级（第 20 秒左右加铺底和弦）。横屏用 100～120 BPM 的电影感科技风，前段克制、高潮段加入弦乐铺底。两版都要求结尾有完整的收束和弦，不能硬切掉。

**卡点方法：** 用节拍检测工具（如 librosa 的节拍追踪）得到每一拍和每个小节的时刻，人工复核重拍；把节拍表写成时间线文件，镜头长度一律以“拍”为单位；推近、硬切、文字弹出、音效都挂在节拍表上。若音乐总长与成片不符，只在段落边界剪辑音乐（按小节剪，交叉淡化 40～80 毫秒），不得中途变速。

**音效：** 准备一套轻量音效——低频冲击、轻点击、柔和的“嗖”声、计数音、部件分离的“咔”声；音效必须真正可闻：把音效放在人声空隙里，开头不能有静音前导。

## 4.5 合成与输出

- 合成器：在第一版的逐帧合成脚本基础上重写，输入改为“60 帧序列 + 节拍时间线 + 交互日志 + 字级时间戳”，输出逐帧画面；文字渲染用抗锯齿、带 1～2 像素柔和投影，保证在亮画面上可读。
- 混音：人声为主；音乐在人声出现时自动压低 6～9 dB，起落 120～200 毫秒；总线轻度限幅；整体 -14 LUFS，真峰值不高于 -1 dBTP。
- 编码：H.264 High Profile，恒定 60 帧每秒，yuv420p，竖屏 1080×1920、横屏 1920×1080；建议码率竖屏 16～20 Mbps、横屏 20～25 Mbps（二次编码或 CRF 16）；音频 AAC 48kHz 256～320 kbps；`faststart`。另外导出一份无字幕版和一份纯音乐版。
- 封面：竖屏封面关键信息放在中间 1080×1464 区域内；横屏封面 1920×1080，标题不超过 10 个字。

# 六、验收清单

制作者交付前逐条自检并附检测结果，任何一条不通过都不得交付。

**帧率与流畅度**

1. 用 ffprobe 确认两版均为恒定 60 帧每秒，总帧数等于时长乘以 60。
2. 用冻结检测（freezedetect，阈值约 0.001、持续 0.3 秒）扫描全片，除片尾最后 0.5 秒和分镜表中声明的“静止推近”外，不得出现冻结段。
3. 对每个运动镜头做相邻帧差分统计：不得出现连续两帧完全相同；不得出现单帧位移远大于前后帧的“跳帧”。
4. 抽查化身数据和整机拆解镜头的任意 2 秒，逐帧查看运动是否均匀连续。

**画面真实性**

5. 每个镜头都能追溯到一段逐帧录制的页面序列；不存在用单张截图推拉冒充的镜头。
6. 画面中没有加载圈、报错提示、调试信息、浏览器地址栏和滚动条残影。
7. 光标点击时刻与页面反应同步（误差不超过 1 帧）。

**节奏与同步**

8. 所有硬切点与节拍表对齐，误差不超过 1 帧；第一版那种 0.3 秒溶解不再作为默认转场。
9. 关键词文字与口播对应字的出现时刻误差不超过 3 帧。
10. 前 3 秒内有至少 2 次视觉变化和 1 个音效；第一帧不是黑场。

**人声（有旁白的版本）**

11. 找 3 位没听过脚本的人盲听，至少 2 位认为“像真人”；否则改用其他配音方案或交付纯音乐版。
12. 无读错字、无吞字、无不自然的长停顿；语速每秒 4～4.5 字。
13. 人声与字幕逐字一致。

**字幕与排版**

14. 所有文字落在第五章安全区内；竖屏单行不超过 14 个字，最多两行。
15. 文字与背景对比清晰；同屏最多一个大标题加一行字幕。

**声音**

16. 整体响度 -14 LUFS（±1），真峰值不高于 -1 dBTP，无削波。
17. 人声出现时音乐压低 6～9 dB；音效在成片中确实可闻；音乐以收束和弦结束。

**内容合规**

18. 全片无商业辅导书品牌、无技术栈文字；站内数量与录制当天线上一致；网址正确。

# 七、风险与回退

| 风险 | 表现 | 应对 | 回退 |
|---|---|---|---|
| 浏览器内核缺失 | 当前沙盒找不到系统浏览器，自动下载失败 | 制作前先恢复浏览器（重装系统包或由上级任务提供） | 恢复前无法录制任何新画面，只能先做配音和音乐 |
| 3D 逐帧太慢 | 1440p 下每帧可能超过 1 秒 | 实测后调整录制分辨率（3D 镜头可用 1.25 倍）、缩短 3D 镜头时长、按“可点击到达的状态”分段 | 3D 镜头改用横屏 1080p 原生分辨率录制，不做大幅推近 |
| 虚拟时间覆盖不全 | 某些动画仍按真实时间跑或卡住 | 逐一排查时间源，补充替换；网页动画用暂停加设置当前时间 | 改用调试协议的受控出帧或虚拟时间策略 |
| v20 部署期间页面变化 | 界面与脚本描述不一致或临时不可用 | 等 v20 上线稳定后再录；录制前跑一遍页面巡检 | 分镜按新界面微调，不改变整体结构 |
| 配音方案未定或效果不达标 | 用户未提供密钥或不录音；盲听不过 | 先完成纯音乐版 | 交付纯音乐 + 动态文字版 |
| 音乐版权识别 | 上传后被自动认领 | 保留许可证书申诉；优先选无版权识别标记的曲目 | 换曲或使用原创合成音乐 |
| 单命令 120 秒限制 | 长任务被中断 | 全部任务分段、可断点续做，每段输出落盘 | 降低分辨率或缩短镜头 |

# 八、需要用户决定的事项

1. **配音方案（最重要）：** A 自己或朋友录音（推荐，最自然、零费用）；B 提供火山引擎豆包语音的 AppID 与 Access Token；C 提供阿里云百炼 API Key；D 提供 MiniMax 或 Azure 的密钥；E 接受纯音乐 + 动态文字版。无论选择哪一项，纯音乐版都会同步制作。
2. **配音音色倾向：** 年轻温和的男声，还是清亮的女声（选 B～D 时需要）。
3. **配乐：** 由制作者在 Pixabay 等曲库中挑 3 首候选供用户试听，还是用户自己指定曲目。
4. **录制时机：** 确认 v20 上线并稳定后再开始正式录制。
